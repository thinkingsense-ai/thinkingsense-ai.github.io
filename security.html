The question

Deep data security, data semantics and NL2SQL, across all sources

I just watched Juan's presentation at AIWorld on data trust (security). He talks about some new features for deep data security (formerly real application security), data semantics, and nl2sql. Hopefully you can provide these capabilities across all data sources.

Andy

We have not seen the talk, so this is our reading of the note: access rules tied to the end user, enforced for people and for AI agents; shared business meaning that policy and AI can rely on; and natural-language questions that obey the rules. The honest summary: row rules and the AI-specific checks are strong and work on any source; column rules, identity at the source, and meaning-based policy are the work that remains.

Profiling suggests personal-data columns for review. The semantic layer is the same for every source. Policy still names physical tables and columns, not terms or tags (G11). Column classification with suggest-and-approve; policy written against tags; masking and model-egress rules that inherit from them.
NL2SQL that respects the rules Generated SQL is never trusted: it is checked after generation (read-only guard and transaction, row and column rules, table-existence check), and the prompt leaves out columns the user may not see. The checks apply to every source. The prompt filter covers the standard schema listing. Sample values and result rows of classified sources, and of tagged columns, no longer go to the model (G4); add an adversarial question suite (G13).
All data sources One policy and one audit trail for SQL databases, files, lakehouse formats, SaaS APIs and agent tools. Coverage differs by connector (see the source tiles in the picture). We tested the policy rewrite on SQL text, not end to end on every connector. Per-connector enforcement tests, and an enforcement mode per source: gateway only, native, or both.
Where ThinkingSense is different. Enforcement inside one database covers that database. A gateway can apply one rule set to a PostgreSQL table, a Parquet file and a SaaS API alike. The strongest design uses both: the gateway for uniform rules and one audit trail, and each database's own row and column security as a second lock, so that neither a gateway bug nor a direct connection is the only line of defence.

G1FixedTested

Column deny and mask grants were bypassed by SELECT * (fixed in main)

What happens
A grant on salary rejected SELECT salary, but SELECT *, e.*, row_to_json(e) and a star inside a subquery or CTE were allowed and returned the column, because the check looked for the column's name in the SQL text.
Why it matters
Anyone who could send SQL (/api/query, the MCP run_sql tool), or whose question led a model to write a star, could read a column they were denied.
Close it by
Fixed in the Server repository: a SQL parser now finds every select-list star and whole-row reference and the table each one reaches. A star that reaches a table with a grant the caller does not satisfy is rejected for a deny grant (SQLSTATE 42501, with a message to list the columns needed), and for a mask grant the column comes back as NULL; a star inside INSERT ... SELECT or CREATE TABLE AS is rejected either way. A statement the parser cannot read is rejected if it contains a star. Quoted table names are now matched too. Table names after a comma (FROM a, employees) are matched too. (effort S)

G3Partly fixedCode

Sources see one shared account, not the end user

What happens
ThinkingSense connects to each source with a configured service account. The user's identity reaches the source only for PostgreSQL (row-level security settings) and Oracle (VPD context), both opt-in. Every other source relies on the gateway alone.
Why it matters
A policy mistake or a compromised gateway exposes whatever the service account can read, and the source's own audit shows one account, not the person. This is the main difference from enforcement that lives inside the database.
Close it by
Per-source enforcement mode: gateway only, native, or both. Add end-user delegation: Oracle end-user or proxy authentication and Deep Data Security grants, SQL Server row-level security, Snowflake row access and masking policies, Databricks Unity Catalog row filters and column masks, BigQuery row access policies. Make every service account SELECT-only and scoped to what the policy allows. Done: native identity for SQL Server (sp_set_session_context), MySQL and MariaDB (@omnigate_* variables for filtering views) and Snowflake (USE ROLE from the user's snowflake_role attribute, session variables, query tag), next to PostgreSQL and Oracle; OMNIGATE_ACCESS_NATIVE_RLS_DIALECT=auto picks the dialect from each connection; a start-up check warns when a PostgreSQL or MySQL service account can do more than read. Native checks run with the gateway's, never instead of them. Not done: Oracle Deep Data Security grants, Databricks Unity Catalog and BigQuery. The new initializers are tested against recorded SQL, not against a live SQL Server, MySQL or Snowflake. G4FixedCode

Data goes to the language model in the default mode

What happens
In the default cloud-first mode the model receives the schema, up to 8 sample values for up to 4 columns per table, the question, and (to phrase an answer) the result rows. There is no redaction and no rule that depends on how sensitive a source is.
Why it matters
Row data and sample values leave your network for any source, including ones you would classify as restricted. Row filters and column grants apply to what the user may see, not to what the model is sent.
Close it by
A source-level egress rule keyed on classification: for restricted sources send no sample values or rows, answer from a local model, or return a table without narration. Redact detected personal data from prompts. Document the data flow for customers' privacy reviews. Done: OMNIGATE_LLM_EGRESS_NO_SAMPLES_FROM and OMNIGATE_LLM_EGRESS_NO_ROWS_FROM keep sample values and result rows of classified sources out of the model (the answer then comes from the deterministic summary); OMNIGATE_LLM_EGRESS_TAGS does the same per column tag; OMNIGATE_LLM_REDACT_PII=true redacts e-mail, social security, card, IBAN and phone patterns; the user guide lists what is sent. Not done: routing a restricted question to a local model. G5FixedCode

SQL and BI tools on the wire protocols have no end-user identity

What happens
The PostgreSQL, MySQL, Oracle and gRPC listeners do not set an end-user identity. When a policy covers a table, those clients are refused (fail-closed); on tables with no policy they are not filtered.
Why it matters
BI tools and scripts cannot get per-user row and column policy. Teams either keep them away from governed tables or leave them unfiltered.
Close it by
Map a wire login to an identity and attributes from the user store or SCIM, then run the same pipeline stages. Add TLS to these listeners (G9). Done: OMNIGATE_WIRE_USERS gives each wire user its own password (read through the secret settings, so it can be encrypted or a reference); PostgreSQL, MySQL, Oracle and gRPC logins run as that user with its provisioned roles and attributes; the shared development credential is off when real users exist and under the strict profile. These protocols need the password on the server to verify the login, so they cannot use one-way hashes. G6FixedCode

Configuration changes are not audited, and the audit log is not durable by default

What happens
Audit events cover sign-in, access decisions, SCIM, questions and governed actions. There is no event for changing the access policy, a data source, a user, the model settings or an OAuth connection. The log is in memory unless OMNIGATE_AUDIT_LOG_DB is set, and there is no built-in export to a SIEM.
Why it matters
You cannot answer who changed a policy, or when. A restart loses the evidence by default.
Close it by
Add a configuration-change event (actor, object, before and after digest) to every admin write; make the durable hash-chained store the default; stream events to syslog, OTLP or a webhook. Done: every successful administrative write records a CONFIG_CHANGED event, and a changed stored value records digests before and after; the durable hash-chained log is kept under the data directory by default; events can stream to a webhook, syslog (UDP) or OTLP/HTTP. G12Partly fixedCode

Policy authoring and masking are basic

What happens
Policy is a YAML file with regular-expression table patterns, edited live. Masking replaces a value with NULL; there is no partial, hashed or format-preserving mask. There is no review step or version history for a policy change.
Why it matters
A broad pattern can scope a rule to the wrong tables unnoticed, and a mask that nulls a value can change an aggregate.
Close it by
Policy versions with review and approval, a before-and-after diff using the existing "test as user" dry run, tests as code, and mask functions (partial, hash, bucket). Done: mask functions (redact, partial:N, bucket:N) in SQL and after the query; policy versions with author, reviewer and digest; OMNIGATE_POLICY_REVIEW=required so a second administrator must approve; a diff against the live version; rollback; and tests kept in the policy file that must pass before a version can go live. Not done: a console page for review (the API is there), and a hash mask (no hash function is shared by every database). Done: mask functions (redact, partial:N, bucket:N) in SQL and after the query; policy versions with author, reviewer and digest; OMNIGATE_POLICY_REVIEW=required so a second administrator must approve; a diff against the live version; rollback; and tests kept in the policy file that must pass before a version can go live. Proof for G1

What the test shows after the fix

Before the fix, the real access-control stage let SELECT * return a column that a deny grant on employees.salary withheld from a user whose role is not hr. After the fix, the same stage gives these results. Row filters, tried the same way, were applied on every shape we tried (see How this was checked).

-- column grant: deny employees.salary unless role = hr; the caller's role is analyst
SELECT salary FROM employees                          REJECTED  caller is not entitled to column "salary"
SELECT name FROM employees                            ALLOWED
SELECT * FROM employees                               REJECTED  list the columns you need
SELECT e.* FROM employees e                           REJECTED
SELECT * FROM (SELECT * FROM employees) t             REJECTED
WITH x AS (SELECT * FROM employees) SELECT * FROM x   REJECTED
SELECT row_to_json(e) FROM employees e                REJECTED
SELECT * FROM "employees"                             REJECTED  (quoted name now matched)
SELECT count(*) FROM employees                        ALLOWED   (not a select-list star)

With a mask grant the same statements run and the salary column is NULL in the result; INSERT ... SELECT * over the table is rejected so the real values cannot be copied. An entitled caller (role = hr) gets the column. The checks are in AccessControlStageStarTest in the Server repository. A table named only after a comma (FROM a, employees) is matched as well.

See it work

A restricted user and a cleared user, same question

Recorded against a running gateway (the Server build with these fixes) in front of a PostgreSQL database with three employees, a SELECT-only service account, and a 1.5-billion-parameter local model answering natural-language questions. Two people are provisioned: alice (clearance=engineering) and bob (clearance=finance). Nothing here is mocked.

The policy that produced everything below

# strict profile: a table no row filter covers is refused, so say that employees needs none
shared_tables: ["employees"]
column_grants:
  # salary is shown to finance only; everyone else sees a band of 10,000
  - table_pattern: employees
    columns: [salary]
    required_attribute: clearance
    allowed_values: [finance]
    on_violation: mask
    mask: bucket:10000
  # anything tagged pii (ssn, once an administrator approves the tag) is refused to everyone else
  - tag: pii
    required_attribute: clearance
    allowed_values: [finance]
    on_violation: deny
tests:
  - name: an engineer cannot read ssn through a star
    sql: SELECT * FROM employees
    user: {id: alice, attributes: {clearance: engineering}}
    expect: denied

Method and limits

A point-in-time review, not a penetration test and not a certification.

  • Run: the real access-control stage with a row filter against 11 SQL shapes (qualified, quoted, upper-case, aliased, subquery, CTE, UNION, left join, trailing comment, a stacked second statement, no attribute) and with a column grant against 6 shapes; the 0.10.11 tests for the read-only guard, the prompt column filter and the security headers; the 0.10.11 image started with a read-only filesystem, as a non-root user, with headers present.
  • Read: the source for authentication, the policy classes, audit event types, secrets handling, TLS usage, model modes, what is sent to the model, and the build workflows.
