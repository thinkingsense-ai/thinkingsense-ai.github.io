The question

Deep data security, data semantics and NL2SQL, across all sources

I just watched Juan's presentation at AIWorld on data trust (security). He talks about some new features for deep data security (formerly real application security), data semantics, and nl2sql. Hopefully you can provide these capabilities across all data sources.

Andy

We have not seen the talk, so this is our reading of the note: access rules tied to the end user, enforced for people and for AI agents; shared business meaning that policy and AI can rely on; and natural-language questions that obey the rules. The honest summary: row rules and the AI-specific checks are strong and work on any source; column rules, identity at the source, and meaning-based policy are the work that remains.

Data semantics: shared meaning policy and AI can use A business catalog (ontology, glossary, metrics, trusted questions). Source-level classification gates dashboard publishing. Profiling suggests personal-data columns for review. The semantic layer is the same for every source. Policy still names physical tables and columns, not terms or tags (G11). Column classification with suggest-and-approve; policy written against tags; masking and model-egress rules that inherit from them.
NL2SQL that respects the rules Generated SQL is never trusted: it is checked after generation (read-only guard and transaction, row and column rules, table-existence check), and the prompt leaves out columns the user may not see. The checks apply to every source. The prompt filter covers the standard schema listing. Sample values of classified sources no longer go to the model (G4, partly); result rows still do; add an adversarial question suite (G13).
All data sources One policy and one audit trail for SQL databases, files, lakehouse formats, SaaS APIs and agent tools. Coverage differs by connector (see the source tiles in the picture). We tested the policy rewrite on SQL text, not end to end on every connector. Per-connector enforcement tests, and an enforcement mode per source: gateway only, native, or both.
Where ThinkingSense is different. Enforcement inside one database covers that database. A gateway can apply one rule set to a PostgreSQL table, a Parquet file and a SaaS API alike. The strongest design uses both: the gateway for uniform rules and one audit trail, and each database's own row and column security as a second lock, so that neither a gateway bug nor a direct connection is the only line of defence.

G1FixedTested

Column deny and mask grants were bypassed by SELECT * (fixed in main)

What happens
A grant on salary rejected SELECT salary, but SELECT *, e.*, row_to_json(e) and a star inside a subquery or CTE were allowed and returned the column, because the check looked for the column's name in the SQL text.
Why it matters
Anyone who could send SQL (/api/query, the MCP run_sql tool), or whose question led a model to write a star, could read a column they were denied.
Close it by
Fixed in the Server repository: a SQL parser now finds every select-list star and whole-row reference and the table each one reaches. A star that reaches a table with a grant the caller does not satisfy is rejected for a deny grant (SQLSTATE 42501, with a message to list the columns needed), and for a mask grant the column comes back as NULL; a star inside INSERT ... SELECT or CREATE TABLE AS is rejected either way. A statement the parser cannot read is rejected if it contains a star. Quoted table names are now matched too. Still open: table names after a comma (FROM a, employees) are not found by the table matcher, so a grant on employees is skipped there; use explicit joins until that is closed. (effort S)
G2FixedDocs

Open by default: with no sign-in configured, the console, API and MCP are open

What happens
If none of local accounts, API tokens or OIDC is set, the admin console, /api/* and /mcp accept anyone. The server logs a warning; nothing stops it.
Why it matters
A quick-start deployment that is later reachable from a network is fully exposed, including the SQL endpoints and every configured data source.
Close it by
Refuse a public bind without sign-in unless an explicit OMNIGATE_INSECURE=true is set; generate a first-boot admin password and print it once (the stacks already do this for the demo database); show a persistent banner while open. Done in the Server repository: the server stops at start with no sign-in unless OMNIGATE_INSECURE=true is set (and never runs open under the strict profile). The Compose quick-starts set it explicitly. Not done: a first-boot admin password for a plain java -jar start, and a banner in the console (the deployment-readiness check already reports an open console as critical). (effort S)
G3HighCode

Sources see one shared account, not the end user

What happens
ThinkingSense connects to each source with a configured service account. The user's identity reaches the source only for PostgreSQL (row-level security settings) and Oracle (VPD context), both opt-in. Every other source relies on the gateway alone.
Why it matters
A policy mistake or a compromised gateway exposes whatever the service account can read, and the source's own audit shows one account, not the person. This is the main difference from enforcement that lives inside the database.
Close it by
Per-source enforcement mode: gateway only, native, or both. Add end-user delegation: Oracle end-user or proxy authentication and Deep Data Security grants, SQL Server row-level security, Snowflake row access and masking policies, Databricks Unity Catalog row filters and column masks, BigQuery row access policies. Make every service account SELECT-only and scoped to what the policy allows. (effort M-L)
G4Partly fixedCode

Data goes to the language model in the default mode

What happens
In the default cloud-first mode the model receives the schema, up to 8 sample values for up to 4 columns per table, the question, and (to phrase an answer) the result rows. There is no redaction and no rule that depends on how sensitive a source is.
Why it matters
Row data and sample values leave your network for any source, including ones you would classify as restricted. Row filters and column grants apply to what the user may see, not to what the model is sent.
Close it by
A source-level egress rule keyed on classification: for restricted sources send no sample values or rows, answer from a local model, or return a table without narration. Redact detected personal data from prompts. Document the data flow for customers' privacy reviews. Done: OMNIGATE_LLM_EGRESS_NO_SAMPLES_FROM keeps sample values of sources classified at or above a level out of the prompt (unclassified sources count as confidential). Not done: result rows are still sent to the model to phrase an answer; no redaction of detected personal data; no local-model routing by classification. (effort M)
G5Partly fixedCode

SQL and BI tools on the wire protocols have no end-user identity

What happens
The PostgreSQL, MySQL, Oracle and gRPC listeners do not set an end-user identity. When a policy covers a table, those clients are refused (fail-closed); on tables with no policy they are not filtered.
Why it matters
BI tools and scripts cannot get per-user row and column policy. Teams either keep them away from governed tables or leave them unfiltered.
Close it by
Map a wire login to an identity and attributes from the user store or SCIM, then run the same pipeline stages. Add TLS to these listeners (G9). Done: a PostgreSQL or MySQL wire login runs as that user, with the roles and attributes provisioned for it, so policy and the audit trail see who asked. Not done: the Oracle and gRPC listeners; separate passwords per wire user (the listener still has one credential); TLS on the MySQL listener. (effort M)
G6FixedCode

Configuration changes are not audited, and the audit log is not durable by default

What happens
Audit events cover sign-in, access decisions, SCIM, questions and governed actions. There is no event for changing the access policy, a data source, a user, the model settings or an OAuth connection. The log is in memory unless OMNIGATE_AUDIT_LOG_DB is set, and there is no built-in export to a SIEM.
Why it matters
You cannot answer who changed a policy, or when. A restart loses the evidence by default.
Close it by
Add a configuration-change event (actor, object, before and after digest) to every admin write; make the durable hash-chained store the default; stream events to syslog, OTLP or a webhook. Done: every successful administrative write records a CONFIG_CHANGED event (actor, route, status, SHA-256 of the body); the durable hash-chained log is kept under the data directory by default; OMNIGATE_AUDIT_LOG_WEBHOOK streams events as JSON. Not done: syslog and OTLP outputs; before and after values of a change. (effort S-M)
G7Partly fixedCode

Secrets are stored as plain values

What happens
Source credentials, OAuth tokens and model keys sit as plain values in the environment or the config store. No encryption at rest was found in the config store. Vault, CyberArk and cloud IAM database tokens are supported for sources, but are not the default.
Why it matters
A copy of the config database, a backup or a support bundle reveals credentials.
Close it by
Envelope-encrypt sensitive values with a key held in a KMS or Vault; make secret references the documented default; add rotation and a startup check that warns on plain values. Done: OMNIGATE_CONFIG_ENCRYPTION_KEY encrypts every configuration-store value (source passwords, tokens, model keys) with AES-GCM, migrates existing values at start, and a warning is logged while it is unset. Not done: a key-management service wrapping the key, rotation, secrets given through environment variables, and other stores (audit, vector, sessions). (effort M)
G8Partly fixedCode

Safe settings are opt-in

What happens
Tables with no policy rule are allowed (the allow-list mode is opt-in), strict column verification is off, the script and style policy is report-only, and HSTS is off.
Why it matters
A new table is readable by anyone who can reach the source until someone writes a rule for it.
Close it by
Ship a strict profile (deny unlisted tables, strict verification) and recommend it; move the style and script policy to enforced after a browser pass; document turning HSTS on once your own certificate is in place. Done: OMNIGATE_SECURITY_PROFILE=strict turns on deny-unlisted-tables, strict column verification, an enforced content security policy and a no-open-access rule together. Not done: making it the default, and HSTS (it needs a certificate browsers trust). (effort S)
G9Partly fixedCode

Internal channels are not all encrypted

What happens
HTTPS and Oracle TCPS can be enabled. No TLS was found on the PostgreSQL and MySQL wire listeners or on the cluster channel between replicas. The stacks start with a self-signed certificate.
Why it matters
Credentials and rows cross the network in clear text on those channels unless the network itself is trusted.
Close it by
TLS for the wire listeners; encrypted, authenticated replica traffic; a documented path to a real certificate on every stack. Done: the PostgreSQL wire listener upgrades a client that asks for TLS (sslmode=require), with OMNIGATE_WIRE_REQUIRE_TLS=true to refuse the rest. Not done: the MySQL listener and the channel between replicas. (effort M)
G10Partly fixedCode

The images the stacks deploy still run as root

What happens
The 0.10.11 images from ghcr.io run as a fixed non-root user. The OCIR and Artifact Registry images the stacks pull are built from a different Dockerfile with no USER.
Why it matters
Code execution in the process starts as root inside the container, and the charts cannot require runAsNonRoot yet.
Close it by
Give those Dockerfiles the same user and directory ownership; then add runAsNonRoot, a read-only root filesystem, dropped capabilities and a default seccomp profile to the charts. The charts already set fsGroup for the volume. Done in a Docker-repository pull request (not yet merged or built): the Dockerfile runs as uid 10001; the app container in all four charts sets runAsNonRoot, no privilege escalation, dropped capabilities and the default seccomp profile. Not done: a read-only root filesystem (the JVM and DuckDB write under /tmp), and no cluster has run the charts yet. (effort S)
G11MediumCode

Classification stops at the source

What happens
Sources can be labelled public to confidential, and the label gates dashboard publishing. There are no column tags. Profiling can suggest personal-data columns for review, but a suggestion does not enforce anything.
Why it matters
Policy refers to physical table and column names. It cannot say "mask everything tagged personal data", and the model-egress rule in G4 has nothing to key on below the source level.
Close it by
Column-level classification with suggest-and-approve; policy written against tags and business terms; masking and model-egress rules that inherit from the tags. (effort M-L)
G12MediumCode

Policy authoring and masking are basic

What happens
Policy is a YAML file with regular-expression table patterns, edited live. Masking replaces a value with NULL; there is no partial, hashed or format-preserving mask. There is no review step or version history for a policy change.
Why it matters
A broad pattern can scope a rule to the wrong tables unnoticed, and a mask that nulls a value can change an aggregate.
Close it by
Policy versions with review and approval, a before-and-after diff using the existing "test as user" dry run, tests as code, and mask functions (partial, hash, bucket). (effort M)
G13Partly fixedCode

Prompt injection is only contained for MCP content

What happens
Tool descriptions and tool output are wrapped as untrusted text. Retrieved documents and data values that flow into prompts are not framed the same way.
Why it matters
A document or a cell value that carries instructions can steer a model. The read-only guard and the row and column checks limit the damage but do not prevent it.
Close it by
Frame all retrieved content as data in every prompt, add an adversarial question suite to CI, and filter outputs that echo instructions. Done: the schema block sent to the model is stated to be data, not instructions, with control characters removed, and result rows in the report prompt are wrapped as untrusted data. Not done: the other narration prompts, an adversarial question suite in CI, and output filtering. (effort S-M)
G14FixedCode

No anti-CSRF token

What happens
State-changing admin routes rely on SameSite=Lax cookies.
Why it matters
Protection depends on the browser, and a same-site subdomain with a script bug weakens it.
Close it by
Require a custom header or a per-session token on state-changing requests. Done: a cookie-authenticated POST, PUT, PATCH or DELETE to /api/ or /app/ must carry X-Requested-With, which the web app now sends. Token clients and cookie-less calls are unaffected. (effort S)
G15Partly fixedCode

No supply-chain or assurance evidence in the repositories

What happens
The only workflow found builds and pushes images. There is no SBOM, image signing, dependency or image vulnerability scan, security contact file, or certification evidence (SOC 2, ISO 27001) in the repositories reviewed.
Why it matters
Customer security reviews will ask. It may exist elsewhere; this review did not find it.
Close it by
Scan dependencies and images in CI, publish an SBOM, sign images, add SECURITY.md with a disclosure address, and start a SOC 2 readiness assessment. Done: SECURITY.md in both repositories (private reporting through GitHub), a dependency scan and CycloneDX SBOM workflow for the Server, and a weekly image scan with SBOM for the Docker images. Not done: image signing, a published SBOM per release, and any SOC 2 or ISO 27001 work. The workflows have not run yet. (effort M)
Proof for G1

What the test shows after the fix

Before the fix, the real access-control stage let SELECT * return a column that a deny grant on employees.salary withheld from a user whose role is not hr. After the fix, the same stage gives these results. Row filters, tried the same way, were applied on every shape we tried (see How this was checked).

-- column grant: deny employees.salary unless role = hr; the caller's role is analyst
SELECT salary FROM employees                          REJECTED  caller is not entitled to column "salary"
SELECT name FROM employees                            ALLOWED
SELECT * FROM employees                               REJECTED  list the columns you need
SELECT e.* FROM employees e                           REJECTED
SELECT * FROM (SELECT * FROM employees) t             REJECTED
WITH x AS (SELECT * FROM employees) SELECT * FROM x   REJECTED
SELECT row_to_json(e) FROM employees e                REJECTED
SELECT * FROM "employees"                             REJECTED  (quoted name now matched)
SELECT count(*) FROM employees                        ALLOWED   (not a select-list star)

With a mask grant the same statements run and the salary column is NULL in the result; INSERT ... SELECT * over the table is rejected so the real values cannot be copied. An entitled caller (role = hr) gets the column. The checks are in AccessControlStageStarTest in the Server repository. Not covered: a table named only after a comma (FROM a, employees).

How this was checked

Method and limits

A point-in-time review, not a penetration test and not a certification.

  • Run: the real access-control stage with a row filter against 11 SQL shapes (qualified, quoted, upper-case, aliased, subquery, CTE, UNION, left join, trailing comment, a stacked second statement, no attribute) and with a column grant against 6 shapes; the 0.10.11 tests for the read-only guard, the prompt column filter and the security headers; the 0.10.11 image started with a read-only filesystem, as a non-root user, with headers present.
  • Read: the source for authentication, the policy classes, audit event types, secrets handling, TLS usage, model modes, what is sent to the model, and the build workflows.
  • Not done: a penetration test, a review of any cloud account or network setup, end-to-end policy tests on each non-SQL connector, a check of anything outside the two repositories (so G15 may exist elsewhere), and anything about the AIWorld talk itself.
