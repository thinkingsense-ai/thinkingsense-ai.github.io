PDF Extract

      
Turns a folder of PDFs into live, queryable data — PDF → AI Extract → Ground → JOIN → Answer. Backed by this project's own PdfFieldExtractor (OCR fallback via PdfOcrEngine when a page has no text layer) — no separate ETL pipeline, no pre-processing step.


      

        
How grounding works
the part that makes this safe to trust

        
1
An LLM proposes field values from the PDF's own text (or OCR text, for a scanned page with no text layer).

        
2
Every proposed value is independently checked against the actual document text — not just trusted because the model said so.

        
3
A value that genuinely appears in the source is marked GROUNDED ✓. A value that doesn't — a rounding, a reformat, a model "correction" — is flagged, never silently used.

        
4
Only grounded values are safe to JOIN against the system of record — an ungrounded field blocks the join for that row rather than risk a false mismatch.

      


      

        
Test schema across documents
answers "does this field list actually work here" before it ships in a query — not after

        
A field name typed into PDF_EXTRACT(...) is a guess about a folder's vocabulary until it's tested against real documents. This samples a batch, runs extraction + grounding on every one, and reports two separate numbers per field — claim rate (does the model find this field at all?) and grounding rate (when it does, is the value actually on the page?) — clustered by which fields each document actually has, so one bad vendor template can't hide inside a blended average.

        

          
          
          
        

        

      


      

        
As SQL, once the schema above tests clean
PDF_EXTRACT() is a real table function — no separate extraction step to run first

        
SELECT x.po_number, x.amount_due AS pdf_amount, x.grounded, po.total_amount AS sap_amount
FROM PDF_EXTRACT('s3://po-documents/', schema => 'po_number,vendor,amount_due') x
JOIN sap_orders.purchase_orders po ON po.po_number = x.po_number
WHERE x.amount_due <> po.total_amount

How it works

        
1
An admin links a Slack channel to a group's data area here, so the right dataset is used for every question asked in that channel.

        
2
A channel member asks by mentioning ThinkingSense in a message — the same NL2SQL and context-check pipeline as Ask runs underneath.

        
3
The answer is posted as a threaded reply, not in the main channel, so the channel stays clean while anyone can still ask a follow-up.

        
4
Access control is enforced per asker, same as Ask — someone without access to a source never sees an answer built from it, in Slack or anywhere else.

How business feedback becomes an ontology fix

        

          
1
Business user flags a bad answer
👎 on a specific answer in Ask, optionally tagged ("wrong join", "missing data", "outdated").

          
2
Feedback attaches to the exact query + join keys used
Not just "this answer was bad" — which relationship the generated SQL actually joined on.

          
3
Repeated flags on the same join surface here
3+ independent flags on the same relationship is a real signal, not one user's opinion — ranked above single-occurrence candidates.

          
4
Admin fixes the relationship, not just the one answer
Every future question using that join benefits — not a one-off patch.
