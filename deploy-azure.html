● Runs in your own Azure subscription

Deploy OmniGate to Microsoft Azure, no local tools required

ThinkingSense is a governed ontology platform for the enterprise. A form-driven Bicep/ARM template brings up a right-sized AKS cluster running OmniGate — ThinkingSense's federated query engine — the Ask App, and a seeded Postgres demo backend, entirely from your browser. Nothing to build, nothing to push: the stack pulls a pre-built image from our own public registry.

Download the template ↓

Opens the Azure Portal's Custom Deployment wizard, pre-loaded from our published Bicep/ARM template. You'll need your own Azure subscription — a free account covers everything this stack defaults to (Ampere Altra quota permitting — see Prerequisites).

What gets deployed

One request, three hops

An Ask App request hits a public Azure Load Balancer, which routes into the AKS cluster to the omnigate pod. omnigate in turn queries the seeded postgres pod over JDBC — that's the whole federated-query path.

What actually happens

Five steps, all in the browser

No Terraform, Docker, or kubectl on your machine for this path — Azure Resource Manager runs the provisioning inside Azure-managed infrastructure, including the Helm install itself (via a deployment script, ARM's answer to a Lambda-backed custom resource).

1

Sign in to your subscription

The Deploy button takes you to Azure Portal sign-in. New to Azure? The free-tier account covers everything this stack defaults to, Ampere Altra regional quota permitting.

2

Custom deployment, pre-loaded

Portal lands on Custom deployment with the template and its form already set to our published release — fetched server-side, nothing to upload yourself.

3

Fill in the wizard

A guided form, not a raw parameters JSON — name a new resource group (the wizard requires "Create new," so this deployment can never end up sharing a resource group with anything else), pick a region, an Ask-app login, and an Anthropic API key. That key is technically optional (the stack deploys fine without one), but the Ask app can't answer any question until it's set, so grab a free key from console.anthropic.com before you start.

4

Review + create

The real provisioning step. Takes roughly 15–20 minutes: the AKS cluster dominates, then the deployment script's Helm install of OmniGate + Postgres.

5

Open the Ask app

The deployment's Outputs tab shows askAppUrl — open it, sign in with the login you set in step 3, and ask a real question.

Clean-room validated end to end on a real Azure subscription (westus2). Getting there surfaced nine real, live-confirmed bugs — a Service CIDR overlap, a missing curl/openssl in the deployment-script container, OCIR rejecting image pulls from a Free Tier tenancy, a silently-disabled login from a malformed user-record format, malformed deployment-script output JSON, kubectl never actually being installed, a Portal CORS failure on the very first real click (GitHub release-asset URLs don't send an Access-Control-Allow-Origin header, which the Portal's wizard needs), and — on the very next real click after that — the Portal wizard's own field defaults silently drifting from the template's defaults (the wizard populates from createUiDefinition.json's own default, not the ARM template's, so a value-only fix in one place invisibly missed the other) — all already fixed. See the stack's README's "Clean-room validated" section for the full list. One more hardening, not yet independently Portal-verified: the wizard now forces "Create new" resource group, since a real deploy targeted a pre-existing shared one.
Prefer the CLI

Same stack, from your terminal

Useful for scripting a deploy, or if you'd rather review the template before Portal ever gets involved.

1

Create a resource group

Pick a region with Ampere Altra availability.

az group create \
  --name omnigate-aks-rg \
  --location westus2  # confirmed live Ampere Altra availability
2

Deploy the template

Pulls the same published Bicep/ARM template.

az deployment group create \
  --resource-group omnigate-aks-rg \
  --template-uri https://github.com/thinkingsense-ai/Docker/releases/download/aks-stack-v1.0.4/azuredeploy.json \
  --parameters appPassword='<plain-text-password>' llmApiKey='<anthropic-api-key>'
Ask-app login: just type a plain username and password in the wizard — appPassword is hashed automatically during deployment, using the deployed image's own hashing utility. No local Docker, no manual hash generation. Full details in the stack's README.
After it's deployed

Check on it, or take it down

There's no need to hunt for individual resources here — an ARM deployment tracks everything it created as one resource group, the same way a CloudFormation stack or an OCI Resource Manager stack does. Two guided scripts in the stack's repo wrap the commands below; clone or download the omnigateaksstack directory to use them.

→

Check on it

Fetches credentials (installing kubectl first if it's missing — confirmed live that az aks get-credentials alone doesn't do that), checks the pods/Services, then actually curls the Ask app to confirm it's serving, not just that Kubernetes reports it as Running.

./verify.sh <your-resource-group>

Or by hand: az aks get-credentials --resource-group <your-rg> --name omnigate-aks, then kubectl get pods / kubectl get svc omnigate-omnigate-http — if EXTERNAL-IP isn't <pending>, that's your Ask app on port 8080.

→

Tear it down

Lists what's in the resource group, asks you to type destroy to confirm, then deletes it — the entire teardown story, since everything the template created lives in that one resource group.

./destroy.sh <your-resource-group>

Or by hand: az group delete --name <your-rg> --yes --no-wait. Full details in the README's Cleanup section.
