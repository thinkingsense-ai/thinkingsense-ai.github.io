Deploy ThinkingSense to Google Cloud, no local tools required

One guided script in Cloud Shell brings up a right-sized Google Kubernetes Engine cluster (Ampere/arm64 nodes, matching the published image), a seeded Postgres demo backend, and ThinkingSense itself. Nothing to build, nothing to push: the stack pulls a pre-built image from our own public registry.

View the stack ↓

Opens Cloud Shell with the repo pre-cloned and the deploy tutorial already queued up. You'll need your own GCP project with billing enabled — start a free trial if you don't have one yet.

What gets deployed

One request, three hops

An Ask App request hits a public GCP Network Load Balancer, which routes into the GKE cluster to the omnigate pod. omnigate in turn queries the seeded postgres pod over JDBC — that's the whole federated-query path.

What actually happens

One script, all in the browser

No Terraform, Docker, or kubectl on your machine for this path — Cloud Shell already has all of them, and a single guided script drives the whole deploy.

1

Sign in to your project

The button opens Cloud Shell with the repo already cloned, and prompts you to pick a GCP project if one isn't set yet — use an existing project with billing already linked, or create one and link billing to it before starting (a brand-new project from the picker won't have billing linked yet, and the setup script checks for that). You'll need the project's Project ID, not its Project Name — GCP allows these to differ.

2

Run the guided script

cd omnigategkestack && ./setup.sh — one script, not a form to hand-fill. It enables the required APIs for you along the way.

3

Answer four prompts

Project/region (defaulted for you), an Ask-app login, and an Anthropic API key — technically optional (the stack deploys fine without one), but the Ask app can't answer any question until it's set, so grab a free key from console.anthropic.com before you start. You can also change it later in the app's Admin console under Models.

4

Confirm the plan

The script runs terraform apply for you and shows exactly what it's about to create — type yes to proceed.

5

Wait for it to finish

Roughly 10–15 minutes: the GKE cluster and node pool, then the ThinkingSense + Postgres Helm release.

6

Open the Ask app

The script prints the kubectl credentials command at the end. Run kubectl get svc omnigate-omnigate-http, open https://<that IP>/, and sign in with the login you set in step 3.

It opens on HTTPS. The first time, your browser will say the certificate is not trusted, because the stack makes its own: choose Advanced, then continue to the site. The connection is encrypted either way; to remove the warning, give the stack your own certificate in the deploy form (Your own certificate).

Choose the demo data. A new install is seeded with an invented supply-chain data set by default. To start with another, set demo_dataset in terraform.tfvars (before the script applies it): it-risk (IT and operational risk at a financial firm), bom (manufacturing bill of materials and sourcing), treasury (cash, payables, hedges and debt across two systems), or all-packs (every pack at once, with a picker in the Ask app). Each comes with approved questions to try. The choice is read on a fresh install only, so changing it later does not reseed; all-packs is the heaviest and needs the most memory and outbound access to GitHub and Hugging Face. With all-packs the Ask app's Workspace dropdown has one entry per pack plus All data. All of the data is invented. See what is in each set, with example questions.
Add Agency (optional). Agency is a second front end for risk management that sits beside the Ask app, with its own address (port 8097) and the same logins. Set install_agency = true in terraform.tfvars before the script applies it. It adds the IT-risk investigation data and a Workspace per pack, and needs about 1 GiB more memory, so use a node with 16 GB: set node_machine_type = "t2a-standard-4". We ran all packs with Agency, workflows and the feed on one t2a-standard-4 node, using under a third of its memory requests. Three more switches, all off by default and all needing install_agency: agency_workflows (the approval workflows: commercial edition only, with your licence and the admin API token; nothing is ever sent to a real system, write-back is a dry run), agency_feed (a small pod reads 12 public news and advisory feeds every 30 minutes and lists matching stories on the Watch screen: headlines and links only, no article text; the publishers' reuse terms have not been reviewed, so it is your call) and agency_tour (a Quickstart tour button for the screens that only read; it signs in nobody else and starts no workflow run). The Agency add-on has had one live GCP deploy, with the settings above.
Before you share the link

Signing in, and who can reach it

Two logins, both set at deploy time. Business users sign in to the Ask app with the login you chose. The admin console (/admin) and the admin API need a separate admin login (user admin), so they are never open to the internet. In terraform.tfvars, omnigate_admin_password is optional (blank = the Ask-app password) and allowed_client_cidrs = "203.0.113.7/32" limits who can connect; run terraform apply again after changing it.

Leave the address list blank for a first try-out and the app is reachable from anywhere. Once you connect real data, set it to your own address or network (Search for your public IP and enter it followed by /32.): the Ask app's agent endpoint answers questions without a login using your Anthropic key, and we are fixing that in the app itself.

HTTPS is on by default and plain HTTP is closed, so passwords and answers are encrypted in transit. With no certificate supplied the stack makes a self-signed one (hence the browser warning above); to use your own, paste a PKCS12 file (base64) and its password into the deploy form and the warning goes away, provided you open the site by the name the certificate is for.

Before you run the script

Project prerequisites

Confirmed live while building this stack — worth checking first, especially on a fresh project.

ResourceNeededWhere to check
BillingA billing account linked to the projectgcloud billing projects describe <project>
APIsKubernetes Engine, Compute Engine, Artifact Registrysetup.sh enables these for you automatically
ComputeT2A (Ampere/arm64) — 2 vCPU / 8GB by defaultService compute.googleapis.com, quota metric T2A_CPUS in your target region

Node count and machine type are adjustable in terraform.tfvars if your project has more headroom — or less. The published image is arm64-only, so any replacement machine type needs to stay on an arm64 (T2A) family.

Prefer the CLI

Same stack, from your terminal

Useful for scripting a deploy, or if you'd rather review the plan yourself before anything gets created. Needs gcloud, terraform, curl, python3, and a JRE installed locally.

1

Clone and authenticate

Same repo Cloud Shell would clone for you.

git clone https://github.com/thinkingsense-ai/Docker.git
cd Docker/resource-manager/omnigategkestack
gcloud auth login
gcloud auth application-default login
2

Run the guided script, or drive Terraform directly

Same script Cloud Shell runs — or skip it and fill terraform.tfvars by hand.

# guided
./setup.sh

# or, by hand
cp terraform.tfvars.example terraform.tfvars
terraform init && terraform apply
Ask-app login: just type a plain username and password when prompted — omnigate_app_password is hashed automatically during apply, using the deployed image's own hashing utility. No local Docker, no manual hash generation. Full details in the stack's README.
After it's deployed

Check on it, or take it down

There's no single "stack" object to look up here the way there is on AWS or OCI — GCP has no equivalent of a CloudFormation stack's Outputs tab or an OCI Resource Manager stack's Outputs group. Checking on (or tearing down) this deployment means talking to the actual GKE cluster directly, from the same Cloud Shell directory (or any other authenticated gcloud/kubectl session) you deployed from.

→

List what's running

Confirms the cluster and node pool are healthy, then points kubectl at them.

gcloud container clusters list --project=<your-project-id>

gcloud container clusters get-credentials omnigate-gke \
  --zone us-central1-a --project=<your-project-id>

kubectl get pods -n default
kubectl get svc omnigate-omnigate-http -n default

If EXTERNAL-IP isn't <pending>, that's your Ask app, at https://<that IP>/.

→

Tear it down

Run from the same omnigategkestack directory you deployed from — reopening via the Cloud Shell button above clones fresh and won't have this deployment's state.

./destroy.sh

Runs terraform destroy when this directory has real state; otherwise offers a confirm-gated fallback that deletes the known resources directly by name. Leaves the Artifact Registry image alone either way — see the README's Cleanup section for that and for the manual gcloud delete commands this falls back to.

Lost your Cloud Shell session? Your files usually aren't gone — Cloud Shell's home directory persists across sessions even though the VM itself is ephemeral. Reopen Cloud Shell directly (not the deploy button above) and look in ~/cloudshell_open/ for the Docker-N clone you were actually using; that's where your terraform.tfstate is. Full details in the README's "Reconnecting to an existing deployment" section.
Later

Upgrading

New releases are linked on this page. To move a running deployment to one, run git pull in your clone, then terraform plan and terraform apply. Your data, settings and licence are kept. Take a backup first (the backup guide has two scripts, tested end to end), and see the upgrade guide for how to go back and what to do if an upgrade fails. From app v0.10.10, Operations → Infrastructure in the admin console shows the replicas, their versions and, for each pod, what the cluster says about it, so you can watch an upgrade (see the guide).
